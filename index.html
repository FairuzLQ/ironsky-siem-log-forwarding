Integrasi IronSKY ke SIEM via Storage Log Forwarding

Panduan langkah demi langkah untuk mengalirkan (feeding) data event keamanan IronSKY dari Amazon S3 ke SIEM Anda. Ditulis serinci mungkin, cocok untuk yang baru pertama kali menyentuh AWS S3 maupun SIEM.

Metode: S3 pull Asumsi: SIEM sudah ready Contoh SIEM: Wazuh Sifat: batch harian (T+1)

Ringkasan

Storage Log Forwarding adalah cara integrasi di mana IronSKY (produk SecIron) menaruh event keamanan aplikasi mobile Anda sebagai file di sebuah Amazon S3 bucket, lalu SIEM Anda menariknya (pull) dari bucket itu untuk dianalisis.

Berbeda dengan integrasi realtime (push langsung), metode ini berbasis file di storage: sederhana, tahan gangguan jaringan, dan tidak perlu membuka port masuk di sisi Anda. Cocok kalau Anda ingin data IronSKY masuk ke SIEM tanpa mengubah aplikasi atau backend.

Untuk Pemula

SIEM (Security Information and Event Management) = sistem yang mengumpulkan log/event keamanan dari banyak sumber, lalu memberi peringatan (alert) jika ada yang mencurigakan. Contoh: Wazuh, Splunk, Elastic Security, IBM QRadar.

Amazon S3 = layanan penyimpanan file di cloud AWS. Anggap seperti "Google Drive"-nya AWS: file disimpan dalam wadah bernama bucket.

Penting: ini batch harian, bukan realtime

IronSKY menulis 1 file per hari per aplikasi, dan file itu di-upload ke S3 keesokan paginya (kira-kira jam 07:00-08:00). Jadi event hari ini baru muncul di SIEM besok pagi. Jika Anda butuh deteksi seketika, gunakan metode integrasi realtime (push/API), bukan panduan ini.

Cara Kerja & Arsitektur

Alurnya sederhana: SecIron mendorong data ke S3, Anda menariknya ke SIEM.

   Aplikasi mobile               SecIron / IronSKY              Amazon S3 (disiapkan SecIron)
   (SDK IronSKY)   ── event ──▶  backend IronSKY   ── tulis ──▶  s3://<bucket>/json_event/<APP_ID>/...
                                                                        │
                                                                        │  (Anda: pull / sync, read-only)
                                                                        ▼
                                        ┌───────────────────────────────────────────────┐
                                        │  Host SIEM / forwarder Anda                     │
                                        │  1) aws s3 sync   → unduh file .json.gz         │
                                        │  2) gunzip + normalisasi → events.jsonl         │
                                        │  3) SIEM baca events.jsonl (log JSON)           │
                                        │  4) rules/decoder → ALERT + dashboard           │
                                        └───────────────────────────────────────────────┘

Bagian yang menjadi tanggung jawab Anda hanyalah kotak "Host SIEM / forwarder". Sisi kiri (aplikasi → IronSKY → S3) sudah diurus SecIron.

Inti panduan ini

Karena SIEM Anda dianggap sudah berjalan, fokus kita cuma: cara mengambil file dari S3 dan menyuapkannya ke SIEM. Itu langkah 1-9 di bawah.

Yang Disiapkan SecIron

Sebelum mulai, SecIron akan memberi Anda akses ke S3 bucket tempat data IronSKY Anda disimpan. Yang Anda terima:

ItemContoh nilaiUntuk apa

Biasanya Access Key ID + Secret dikirim dalam satu file accessKeys.csv (unduhan standar dari AWS Console) dengan isi seperti:

accessKeys.csv

Untuk Pemula: apa itu Access Key?

Program (seperti AWS CLI) tidak login pakai email/password. Ia login pakai sepasang kunci: Access Key ID (mirip username) dan Secret Access Key (mirip password). Keduanya bersama membuktikan "saya berhak akses". Karena itu Secret harus dijaga rahasia.

Izin (permission) yang diberikan

Kunci yang diberikan SecIron bersifat read-only dan hanya untuk prefix Anda. Secara teknis izinnya kira-kira:

Aksi S3Arti
s3:ListBucketBoleh melihat daftar file di bucket/prefix Anda
s3:GetObjectBoleh mengunduh isi file

Anda tidak bisa menghapus/menulis. Itu memang tujuannya, cukup untuk menarik data.

Wajib: amankan kredensial

Access Key adalah rahasia setara password. Jangan commit ke Git, jangan tempel di chat/ticket publik, jangan taruh di dokumen yang bisa diakses banyak orang. Kalau bocor, minta SecIron me-rotate (ganti) kuncinya.

Struktur & Format Data batch T+1

Di mana file-nya?

File tersusun berdasarkan aplikasi dan tanggal, dengan pola path (prefix) seperti ini:

Pola path di S3
s3://<bucket>/json_event/<APP_ID>/<TAHUN>/<BULAN>/<TANGGAL>-event.json.gz

contoh nyata:
s3://seciron-acme-events/json_event/1141/2026/09/2026-09-16-event.json.gz
Untuk Pemula: apa itu "prefix"?

S3 sebenarnya tidak punya folder sungguhan, tapi nama file bisa mengandung garis miring / sehingga terlihat seperti folder. Bagian awal nama itu disebut prefix. Jadi json_event/1141/2026/09/ berperan seperti "folder".

Format file

  • File di-gzip (berakhiran .gz) supaya kecil. Isi setelah di-unzip adalah NDJSON.
  • NDJSON = "Newline-Delimited JSON": satu objek JSON per baris (bukan satu array besar). Ini format ideal untuk log.
  • File lama mungkin berakhiran .tar.gz (arsip tar berisi JSON). Panduan ini menangani keduanya.
  • 1 file = 1 hari event untuk 1 aplikasi.

Isi 1 event (contoh)

satu baris di dalam *-event.json.gz
{
  "udid": "1a2b3c4d-0000-demo-udid-999999999999",
  "user_udid": "unknow",
  "app_id": "1141",
  "app_name": "Contoh Bank App",
  "app_version": "1.0",
  "Security event": "event_risk_root",
  "start_id": "1789534198552",
  "os_version": "13",

Arti field penting

FieldArti
Security eventJenis ancaman yang dideteksi (mis. event_risk_root, event_high_risk_MITM_android). Ini field paling penting.
udidID unik perangkat. Untuk mengelompokkan event per device.

Field seperti Security event, Response type, Client response mengandung spasi. Banyak SIEM susah membuat rule untuk field bernama begitu. Karena itu di Langkah 6 kita ubah (normalisasi) menjadi security_event, response_type, dst.

Prasyarat di Sisi SIEM

Anggap SIEM sudah terpasang dan jalan. Yang perlu disiapkan untuk feeding S3:

KebutuhanKeterangan

Tidak harus di server SIEM

Anda boleh menjalankan pengambilan di mesin lain (forwarder), lalu meneruskan file ke SIEM. Yang penting hasil akhirnya: file event terbaca oleh SIEM.

Langkah 1 — Simpan Kredensial dengan Aman

AWS CLI membaca kredensial dari file ~/.aws/credentials. Kita buat sebuah "profil" bernama ironsky agar tidak tercampur dengan kredensial AWS lain.

buat profil ironsky (Linux/macOS)
mkdir -p ~/.aws && chmod 700 ~/.aws

# tulis profil (ganti nilainya dengan kunci dari SecIron)
cat >> ~/.aws/credentials <<'EOF'
[ironsky]
aws_access_key_id = AKIAxxxxxxxxxxxxMRMQ
aws_secret_access_key = wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY
EOF

chmod 600 ~/.aws/credentials
Jangan simpan kunci di dalam repo/script

Selalu taruh di ~/.aws/credentials (permission 600), bukan di dalam file script yang mungkin ikut ter-commit. Tambahkan *.csv dan .aws/ ke .gitignore Anda.

Langkah 3 — Konfigurasi Profil & Region

Set region default untuk profil ironsky supaya tidak perlu mengetik --region terus. Gunakan region yang diberi SecIron (contoh Jakarta = ap-southeast-3).

set region
aws configure set region ap-southeast-3 --profile ironsky
aws configure set output json --profile ironsky
Untuk Pemula: apa itu region?

AWS punya banyak data center di dunia (region). Sebuah bucket "tinggal" di satu region. Kalau Anda pakai region salah, akses bisa gagal/redirect. Tanyakan region bucket ke SecIron.

Langkah 4 — Tes Akses

Pastikan kunci & izin bekerja sebelum lanjut. Pertama cek identitas kunci:

cek identitas
aws sts get-caller-identity --profile ironsky

Lalu daftar isi prefix Anda (ganti bucket & APP_ID):

list file di prefix Anda
aws s3 ls s3://<bucket>/json_event/<APP_ID>/ --recursive --profile ironsky | tail

Output yang sehat kira-kira:

contoh output
2026-09-16 07:15:03   5971 json_event/1141/2026/09/2026-09-15-event.json.gz
2026-09-17 07:15:03   3324 json_event/1141/2026/09/2026-09-16-event.json.gz
Jebakan umum

Jika muncul AccessDenied, InvalidAccessKeyId, atau PermanentRedirect, lihat bagian Troubleshooting, hampir selalu soal region, salah ketik kunci, atau prefix keliru.

Langkah 5 — Tarik Data (aws s3 sync)

aws s3 sync hanya mengunduh file yang belum ada di lokal (incremental), jadi aman dijalankan berulang.

sync ke folder lokal
mkdir -p /opt/ironsky/raw

aws s3 sync s3://<bucket>/json_event/<APP_ID>/ /opt/ironsky/raw/ \
  --profile ironsky --region ap-southeast-3 \
  --exclude "*" --include "*.json.gz" --include "*.tar.gz"
Kenapa pakai sync, bukan cp?

sync otomatis melewati file yang sudah ada, jadi kalau dijalankan tiap 30 menit ia hanya mengunduh file hari baru, hemat bandwidth.

Langkah 6 — Ekstrak & Normalisasi

Setelah file terunduh, kita buka gzip-nya dan (disarankan) rapikan nama field agar SIEM mudah memproses.

6a. Buka gzip

lihat isi 1 file
# file .json.gz  → NDJSON langsung
gunzip -c /opt/ironsky/raw/2026/09/2026-09-16-event.json.gz | head -2

# file lama .tar.gz → keluarkan semua anggota ke stdout
# tar -xzOf /opt/ironsky/raw/.../2026-01-25-event.tar.gz

6b. Normalisasi field (disarankan)

Simpan script kecil ini. Ia mengubah key berspasi jadi snake_case dan membungkusnya di bawah ironsky supaya rapi (mis. Security event → ironsky.security_event).

ironsky_normalize.py
#!/usr/bin/env python3
import sys, json, re
def snake(k): return re.sub(r"[^a-z0-9]+","_",k.strip().lower()).strip("_")
for raw in sys.stdin:
    raw = raw.strip()
    if not raw: continue
    try: ev = json.loads(raw)
    except json.JSONDecodeError: continue
    if not isinstance(ev, dict): continue
    norm = {snake(k): v for k, v in ev.items()}
    print(json.dumps({"integration":"ironsky","ironsky":norm}, ensure_ascii=False))
jalankan: gzip → normalisasi → events.jsonl
mkdir -p /opt/ironsky/out
gunzip -c /opt/ironsky/raw/2026/09/*.json.gz \
  | python3 /opt/ironsky/ironsky_normalize.py \
  >> /opt/ironsky/out/events.jsonl
Hasil normalisasi (1 baris)

{"integration":"ironsky","ironsky":{"security_event":"event_risk_root","udid":"...","app_name":"...", ...}}

Sekarang field bisa dirujuk sebagai ironsky.security_event dan mudah dibuatkan rule.

Langkah 7 — Feeding ke SIEM

Tujuannya: buat SIEM membaca file events.jsonl sebagai log JSON. Ada dua pendekatan.

Opsi A — Puller + file log (disarankan, paling fleksibel)

SIEM (atau agent-nya) memantau sebuah file, dan kita terus menambahkan event ke file itu. Ini bekerja di hampir semua SIEM.

Wazuh — tambahkan ke /var/ossec/etc/ossec.conf
<ossec_config>
  <localfile>
    <log_format>json</log_format>
    <location>/opt/ironsky/out/events.jsonl</location>
  </localfile>
</ossec_config>
restart Wazuh manager
sudo systemctl restart wazuh-manager

Padanan di SIEM lain:

SIEMCara membaca events.jsonl
Wazuh<localfile> dengan log_format json (di atas)
ElasticFilebeat input filestream + ndjson parser
SplunkUniversal Forwarder monitor:///opt/ironsky/out/events.jsonl (sourcetype _json)
GraylogFilebeat/Fluentd → GELF/Beats input

Opsi B — Modul S3 native SIEM

Beberapa SIEM punya modul penarik S3 sendiri (Wazuh aws-s3 wodle, Splunk Add-on for AWS, Elastic S3 input). Praktis, tapi modul native sering mengharapkan format log tertentu dan kurang cocok dengan arsip harian .json.gz/.tar.gz.

Rekomendasi

Untuk format IronSKY (arsip harian gzip NDJSON), Opsi A paling andal karena kita mengendalikan langkah ekstrak + normalisasi sebelum SIEM membacanya.

Langkah 8 — Otomatisasi (Jadwalkan)

Bungkus Langkah 5-6 jadi satu script yang idempotent (tidak memproses ulang file yang sudah pernah diproses), lalu jadwalkan.

/opt/ironsky/pull.sh
#!/usr/bin/env bash
set -euo pipefail
BUCKET="<bucket>"; APP="<APP_ID>"; REGION="ap-southeast-3"; PROFILE="ironsky"
RAW=/opt/ironsky/raw; OUT=/opt/ironsky/out/events.jsonl
STATE=/opt/ironsky/processed.list; NORM=/opt/ironsky/ironsky_normalize.py
export AWS_PAGER=""
mkdir -p "$RAW" "$(dirname "$OUT")"; touch "$STATE" "$OUT"

aws s3 sync "s3://$BUCKET/json_event/$APP/" "$RAW/" \
  --profile "$PROFILE" --region "$REGION" \
  --exclude "*" --include "*.json.gz" --include "*.tar.gz" --only-show-errors

extract(){ case "$1" in *.json.gz) gunzip -c "$1";; *.tar.gz) tar -xzOf "$1";; esac; }

while IFS= read -r -d '' f; do
  key="${f#"$RAW"/}"
  grep -qxF "$key" "$STATE" && continue          # sudah diproses → lewati
  extract "$f" | python3 "$NORM" >> "$OUT"
  echo "$key" >> "$STATE"
done < <(find "$RAW" -type f \( -name '*.json.gz' -o -name '*.tar.gz' \) -print0 | sort -z)
echo "done: $(wc -l < "$OUT") events total"
jadwal via cron (tiap 30 menit)
chmod +x /opt/ironsky/pull.sh
( crontab -l 2>/dev/null; echo "*/30 * * * * /opt/ironsky/pull.sh >> /var/log/ironsky-pull.log 2>&1" ) | crontab -
Alternatif: systemd timer

Jika Anda lebih suka systemd, buat ironsky-pull.service (Type=oneshot, ExecStart=/opt/ironsky/pull.sh) + ironsky-pull.timer (OnUnitActiveSec=30min) lalu systemctl enable --now ironsky-pull.timer.

Ingat sifat T+1

Menjadwalkan tiap 30 menit tidak membuat data jadi realtime, ia hanya memastikan file harian terambil segera setelah SecIron meng-upload-nya (pagi hari). Sepanjang hari, biasanya tidak ada file baru.

Langkah 9 — Parsing & Deteksi (opsional, tapi ini "nyawa" SIEM)

Setelah event masuk, SIEM otomatis mem-parse JSON menjadi field (mis. Wazuh membuat data.ironsky.security_event). Langkah berikutnya: buat rule agar tiap jenis ancaman diberi level & masuk dashboard.

Wazuh — contoh rule (petik dari /var/ossec/etc/rules/)
<group name="ironsky,seciron,">
  <rule id="100100" level="3">
    <field name="ironsky.security_event" type="pcre2">.+</field>
    <description>IronSKY event: $(ironsky.security_event)</description>
  </rule>

  <rule id="100106" level="12">
    <if_sid>100100</if_sid>
    <field name="ironsky.security_event" type="pcre2">^event_risk_root$</field>
    <description>IronSKY: rooted device ($(ironsky.udid))</description>
    <mitre><id>T1548</id></mitre>
    <group>rooting,</group>
  </rule>
</group>
Catatan MITRE ATT&CK

DB MITRE bawaan Wazuh memakai matriks Enterprise. ID teknik Mobile akan diabaikan diam-diam. Pakai padanan Enterprise, mis. root → T1548, injeksi/Frida → T1055, emulator → T1497.001, MITM → T1557, keylogger → T1056.001, screen capture → T1113, sideload → T1204.002, anti-debug → T1622.

Buat satu rule per jenis security_event (root, frida/injection, emulator, MITM, keylogger, accessibility, dsb) dengan level sesuai tingkat bahaya. Setelah itu, dashboard & alert SIEM Anda akan terisi otomatis.

Verifikasi End-to-End

  1. File terunduh? ls -R /opt/ironsky/raw | tail
  2. events.jsonl bertambah? wc -l /opt/ironsky/out/events.jsonl
  3. SIEM menerima? Di Wazuh: cek /var/ossec/logs/alerts/alerts.json atau dashboard → filter rule.groups: ironsky.
  4. Tes 1 baris (Wazuh): pastikan rule cocok.
tes cocok-tidaknya rule
tail -1 /opt/ironsky/out/events.jsonl | sudo /var/ossec/bin/wazuh-logtest

FAQ

Apakah ini realtime?

Tidak. Ini batch harian (T+1). Untuk deteksi seketika, gunakan integrasi realtime (push/API) dari IronSKY.

Berapa lama data tersimpan di S3?

Sesuai kebijakan retensi SecIron. Tanyakan agar Anda tahu seberapa jauh histori bisa ditarik.

Bisakah pakai IAM Role, bukan Access Key?

Jika SIEM Anda berjalan di AWS dan bucket berbagi akun/lewat cross-account role, ya. Untuk lintas-organisasi, biasanya SecIron memberi Access Key statis seperti di panduan ini.

SIEM saya bukan Wazuh, apakah tetap bisa?

Bisa. Konsepnya identik: pull dari S3 → ekstrak/normalisasi → suapkan file JSON ke SIEM → buat rule. Hanya sintaks konfigurasi ingest & rule yang berbeda per produk.

Apakah aman menaruh Access Key di server?

Aman jika di ~/.aws/credentials dengan permission 600, tidak di-commit, dan diakses hanya oleh user yang menjalankan job. Rotasi kunci bila dicurigai bocor.
